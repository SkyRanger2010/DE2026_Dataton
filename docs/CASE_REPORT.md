# Отчёт по кейсу: построение инфраструктуры хранилища данных (Билайн)

**Проект:** DE2026_Dataton  
**Контекст:** практический кейс по построению единой платформы данных для телеком-компании при разрозненном хранении данных в разных БД и отсутствии интеграции с внешними источниками.

---

## 1. Ожидаемые результаты кейса

По условиям кейса ([sample_data/DESCRIPTION.md](../sample_data/DESCRIPTION.md)) ожидалось следующее.

### 1.1. Цели

- Разработать **инфраструктуру для ML и BI** в единой архитектуре платформы данных.
- Реализовать **архитектуру хранилища данных** с описанием ETL-пайплайнов загрузки.
- Предложить **вариант реализации BI-инструментов и ML-модели**.

### 1.2. Исходные данные (CSV)

| Набор | Файл | Назначение |
|-------|------|------------|
| Показы/клики по баннерам | Fct_banners_show | События по баннерам и кампаниям |
| Установки приложения | Installs | user_id, install_timestamp, source |
| Поведение после установки | Fct_actions | user_id, session_start, actions |
| Метаданные баннеров | CD_banner | creative_type, message, size, target_audience_segment |
| Кампании | CD_campaign | daily_budget, start_date, end_date; **CPM/CPC рассчитать** |
| Пользователи | CD_user | segment, tariff, date_create, date_end |

### 1.3. Критерии выполнения кейса

Кейс считается выполненным, если:

1. **Описаны фреймворки и сущности** для работы с данными.
2. **Описаны базы и формат хранения** данных.
3. **Приведено обоснование и допущения**, в рамках которых решение работает.
4. **Приведены реальные кейсы** реализации потоков загрузки данных, моделей и BI.

Дополнительно в требованиях: обоснование выбора фреймворков, учёт масштабируемости и количества запросов.

## 2. Реализованное решение

### 2.1. Архитектура

Реализована платформа с единым потоком данных:

```
Источники (CSV / Kafka)  →  Kafka  →  Spark (ETL)  →  Iceberg (MinIO)
                                                           ↓
                                            raw → ods → dm / ml
                                                           ↓
Trino (SQL)  →  Superset (BI)   и   ML-модель (прогноз клика)
```

Оркестрация: **Airflow** (DAG-и с зависимостями задач, retry, запуск Spark).

### 2.2. Фреймворки и сущности

| Компонент | Роль |
|-----------|------|
| **Kafka** | Приём и буферизация событий (banner_events, installs, actions и др.). |
| **Spark** | ETL: загрузка raw из Kafka/CSV, нормализация ODS, расчёт витрин и ML-признаков. |
| **Airflow** | Оркестрация пайплайнов, расписание, запуск Spark-задач. |
| **Iceberg** | Формат хранения таблиц (raw, ods, dm, ml) в S3-совместимом хранилище. |
| **Trino** | SQL-запросы к Iceberg для BI и проверки данных. |
| **Superset** | Дашборды и отчёты по витринам. |
| **XGBoost / scikit-learn** | ML: модель прогноза клика (CTR), batch-инференс. |

Сущности: пользователь, баннер, кампания, показ/клик (fct_banners / banner_events), установка (installs), действие (fct_actions), справочники (cd_banner, cd_campaign, cd_user). Схемы и правила нормализации описаны в каталоге `iceberg/` (schema_ods_er.md, schema_banner_events.md, schema_ml.md).

### 2.3. Базы и формат хранения

- **PostgreSQL (postgres-airflow):** метаданные Airflow и Superset.
- **PostgreSQL (postgres-meta):** метаданные Hive Metastore (каталог Iceberg).
- **MinIO:** S3-совместимое хранилище, бакет `warehouse`; в нём лежат данные Iceberg в формате **Parquet**, партиционирование по дате.
- **Kafka:** топики для потоковых событий до обработки Spark.

Слои в Iceberg: **raw** (сырые данные), **ods** (нормализованный слой с очисткой и дедупликацией), **dm** (витрины для BI), **ml** (витрина признаков и предсказания).

### 2.4. Обоснование и допущения

- **Kafka** выбран для надёжной доставки потоков и отвязки источников от потребителей.
- **Spark** — единый движок для batch и streaming ETL, нативная поддержка Iceberg и Kafka.
- **Iceberg** даёт ACID, версионирование и совместимость со Spark и Trino без привязки к HDFS.
- **MinIO** используется как S3-совместимое хранилище в локальном/корпоративном контуре.
- **Trino** обеспечивает быстрые интерактивные запросы к Iceberg для BI.

**Допущения MVP:** в качестве источников — CSV (sample_data) и/или симуляция в Kafka; один брокер Kafka и один кластер Spark для демо; витрина обновляется по расписанию (ежедневно); при отсутствии части ODS (installs, fct_actions) в витрине допускаются нули по соответствующим метрикам. В этих рамках решение воспроизводимо и работоспособно.

### 2.5. Реализованные потоки загрузки

| Поток | Реализация |
|-------|------------|
| Kafka → raw → ods → dm.campaign_daily | DAG **banner_events_pipeline**, Spark-скрипты kafka_to_raw.py, raw_to_ods.py, ods_to_dm.py. |
| CSV → raw → ODS → dm.campaign_daily (полные метрики) | DAG **csv_pipeline**, csv_to_raw_iceberg.py, raw_to_ods_iceberg.py, ods_to_dm_full.py. Расчёт CPM/CPC по эталонной логике. |
| Прямая загрузка в Trino (демо) | SQL-скрипты dm_campaign_daily_fill.sql, ml_demo_fill.sql; генерация из CSV — generate_demo_fill_from_csv.py. |
| Витрина признаков для ML | Spark build_ml_user_features.py, DAG **ml_daily_pipeline**. Запись в ml.user_features. |

### 2.6. Реализация ML

- **Витрина признаков** ml.user_features: показы/клики за 7 дней, recency, device_type, os, segment, tariff (источники — ods.banner_events, при наличии ods.fct_actions, ods.cd_user).
- **Обучение модели** (ml/train.py): XGBoost, целевая метка — наличие клика (clicks_7d > 0), метрика ROC-AUC.
- **Инференс** (ml/inference.py): расчёт probability_click и рекомендации ставки (recommend_bid) по сегменту (high_spend +20%, low_active стандарт и т.д.).

### 2.7. Реализация BI

- **Подключение Superset к хранилищу:** Trino, каталог iceberg, датасет по витрине **dm.campaign_daily** (инструкция в docs/SUPERSET_MVP.md, bi/superset_connection.md).
- **Дашборд «Эффективность кампаний»:** чарты по CTR, показам и кликам по кампаниям и дням; метрики и формулы соответствуют эталону docs/sql/dm_campaign_daily.sql (в т.ч. CPM/CPC, рассчитанные по условию кейса).
- Экспорт/импорт дашбордов описан в bi/dashboards/README.md.

## 3. Альтернативы решению

Ниже — альтернативные варианты по ключевым звеньям платформы и краткое сравнение с выбранным решением.

### 3.1. Потоковая шина вместо Kafka

| Вариант | Описание |
|---------|----------|
| **Apache Pulsar** | Единая шина для потоков и очередей, мультитенантность, гео-репликация. Сложнее в эксплуатации, меньше готовых коннекторов к Spark/CDC. |
| **RabbitMQ** | Очереди с гибкой маршрутизацией. Проще Kafka, но нет долгого хранения логов, слабее масштабирование по партициям и повторное чтение. |
| **Kafka (выбрано)** | Стандарт для событийных потоков, богатая экосистема (Kafka Connect, Spark, Debezium), отличная масштабируемость и retention. |

### 3.2. ETL-движок вместо Spark

| Вариант | Описание |
|---------|----------|
| **Apache Flink** | Упор на streaming, низкая задержка, ровная обработка. Сложнее интеграция с Iceberg и batch-витринами, выше порог входа. |
| **dbt + Python** | SQL-центричный ETL, версионирование моделей. Требует отдельного движка выполнения (Warehouse/Spark); слабее для потоковой загрузки из Kafka. |
| **Spark (выбрано)** | Единый движок для batch и streaming, нативная поддержка Iceberg и Kafka, привычная модель для хранилищ данных. |

### 3.3. Формат хранения вместо Iceberg

| Вариант | Описание |
|---------|----------|
| **Delta Lake** | ACID, time travel, тесная интеграция со Spark. Сильнее завязан на экосистему Databricks; поддержка в Trino ограничена. |
| **Apache Hudi** | Упор на инкременты и upsert. Сложнее схема и настройка; экосистема меньше, чем у Iceberg. |
| **Iceberg (выбрано)** | Нейтральный формат, поддержка Spark и Trino, развитие в Apache; подходит для MinIO/S3 без HDFS. |

### 3.4. Оркестрация вместо Airflow

| Вариант | Описание |
|---------|----------|
| **Prefect / Dagster** | Современный Python-ориентированный оркестратор, удобный DX. Меньше готовых интеграций с Hadoop/Spark и корпоративными системами. |
| **Kubernetes CronJobs / Argo** | Запуск задач в K8s по расписанию. Гибко, но нет явных DAG-зависимостей и UI для мониторинга пайплайнов «из коробки». |
| **Airflow (выбрано)** | Явные DAG-и, зависимости, retry, богатая экосистема и интеграции; де-факто стандарт для data-пайплайнов. |

### 3.5. BI вместо Superset + Trino

| Вариант | Описание |
|---------|----------|
| **Metabase + прямой доступ к БД** | Простой BI, быстрый старт. Нет единого SQL-слоя к Iceberg; при нескольких источниках дублирование подключений и логики. |
| **Tableau / Power BI + коннекторы** | Мощная визуализация, корпоративные фичи. Высокая стоимость лицензий; интеграция с Iceberg через отдельные коннекторы/прокси. |
| **Superset + Trino (выбрано)** | Open Source, один слой доступа (Trino) ко всем витринам Iceberg, гибкие дашборды и SQL Lab. |

### 3.6. Хранилище вместо MinIO

| Вариант | Описание |
|---------|----------|
| **HDFS** | Классическое хранилище для Hadoop. Требует отдельного кластера, сложнее в контейнеризации и гибридных сценариях. |
| **Облачный S3 (AWS/GCS)** | Масштабируемость и сервисная модель. Зависимость от облака и бюджета; для MVP/онпрем удобнее локальный S3-совместимый слой. |
| **MinIO (выбрано)** | S3-совместимый API, запуск on-prem или в любом облаке, один стек с остальными компонентами в Docker. |

## 4. Сравнительная таблица: наше решение vs альтернативы

| Критерий | Наше решение | Альтернатива | Лучше / хуже |
|----------|--------------|--------------|--------------|
| **Потоковая шина** | Kafka | Pulsar, RabbitMQ | **Лучше:** максимальная совместимость со Spark, Debezium, Kafka Connect; отраслевой стандарт для событий. **Хуже:** RabbitMQ проще поднять для простых очередей; Pulsar сильнее при мультитенантности и гео-репликации. |
| **ETL-движок** | Spark | Flink, dbt | **Лучше:** один движок для batch и streaming, нативная работа с Iceberg и Kafka, типичный выбор для data lake. **Хуже:** Flink даёт меньшую задержку в чистом streaming; dbt проще для чисто SQL-команд. |
| **Формат таблиц** | Iceberg | Delta, Hudi | **Лучше:** независимость от вендора, поддержка Spark и Trino, активное развитие в Apache. **Хуже:** Delta удобнее в экосистеме Databricks; Hudi сильнее в сценариях частых upsert. |
| **Оркестрация** | Airflow | Prefect, K8s CronJobs | **Лучше:** явные DAG-и, UI, множество интеграций, привычен для data-инженеров. **Хуже:** Prefect/Dagster приятнее в разработке на Python; K8s даёт больше гибкости в инфраструктуре. |
| **BI** | Superset + Trino | Metabase, Tableau/Power BI | **Лучше:** open source, один слой доступа (Trino) ко всем данным Iceberg, без лицензий. **Хуже:** Tableau/Power BI богаче по визуализации и корпоративным функциям; Metabase проще для быстрого старта без Trino. |
| **Хранилище** | MinIO | HDFS, облачный S3 | **Лучше:** один Docker-стек, S3 API, не привязаны к облаку. **Хуже:** облачный S3 масштабируется и управляется провайдером; HDFS привычен в чисто Hadoop-окружении. |
| **Сложность стенда** | Средняя (много сервисов) | Упрощённый вариант (только Postgres + dbt + Metabase) | **Наше лучше:** полный цикл поток → хранилище → BI/ML, приближен к production. **Хуже:** для демо «только отчёт» проще один Postgres + BI. |
| **Масштабируемость** | Партиции Kafka/Spark, добавление воркеров | Зависит от альтернативы | **Наше лучше:** горизонтальное масштабирование Kafka и Spark, Iceberg без блокировок на запись. **Хуже:** при очень низком объёме данных тяжёлый стек избыточен. |

**Вывод:** выбранный стек (Kafka, Spark, Iceberg, Airflow, Trino, Superset, MinIO) даёт сбалансированное решение для единой платформы данных с потоковой загрузкой, витринами и BI при сохранении открытости и возможности масштабирования. Альтернативы выигрывают в узких сценариях (минимальная задержка — Flink, только SQL — dbt, максимальная простота — RabbitMQ + Metabase), но проигрывают в полноте и унификации потока данных.

## 5. Итог


1. Описаны **фреймворки и сущности** для работы с данными (Kafka, Spark, Airflow, Iceberg, Trino, Superset, ML-стек; сущности и нормализация ODS).
2. Описаны **базы и формат хранения** (PostgreSQL, MinIO, Kafka; Iceberg/Parquet, слои raw/ods/dm/ml).
3. Приведены **обоснование выбора компонентов и допущения** MVP, в рамках которых решение работоспособно и воспроизводимо (Docker Compose).
4. Реализованы **реальные кейсы**: потоки загрузки из Kafka и CSV в витрину dm.campaign_daily (в т.ч. с расчётом CPM/CPC), сбор ML-витрины и пайплайн модели прогноза клика, BI-дашборд в Superset по витрине с эталонными метриками.

Все артефакты (код, DAG-и, скрипты, схемы, документация) находятся в репозитории; запуск платформы выполняется командой `docker compose up -d` после копирования `.env.example` в `.env`.
